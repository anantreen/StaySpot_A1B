**Transaction rationale:** PostgreSQL forbids transaction termination inside an exception-handling block, and a procedure invoked inside an explicit transaction cannot end it itself. Those restrictions explain the caller-owned design. [PostgreSQL transaction management](https://www.postgresql.org/docs/16/plpgsql-transactions.html), [CALL rules](https://www.postgresql.org/docs/16/sql-call.html).

**Isolation wording:** the booking API issues plain `BEGIN`; it does not explicitly request REPEATABLE READ. The supplied Assignment 1 **Project 3** Workflow 1 text asks for a PL/pgSQL booking transaction and graceful rollback without explicitly naming REPEATABLE READ. Transaction boundaries being in the API should still be explained honestly in the viva; it is not accurate to describe the procedure as committing internally.

## 5. Performance and outstanding requirements

1. **Frontend booking history remains a gap.** [useBookingHistory](../members/member1/web/hooks/useBookingHistory.js) follows every matching ascending API page, sorts the combined array by timestamp/ID and then displays 20 rows. For M matching records this requires O(M) retained records and O(M log M) sorting, plus all page requests. A 50-row API limit does not make the entire browser load bounded.
2. **Audit also accumulates a scope.** [useAuditHistory](../members/member2/web/hooks/useAuditHistory.js) fetches every matching page for one guest/date range and reverses it: O(A) retained records and reversal work for A matches. Stored running balances are preserved. This should not be described as one-page network loading.
3. **Analytics optimization changes scope and rank meaning.** The old global historical report and current selected-property/date report are not interchangeable benchmarks. The historical performance report separately explains its same-scope comparator. No timings or execution plans were recaptured during this review.
4. **Index use is not a universal complexity guarantee.** Output limits do not bound every query's examined candidates; materialized refresh and matching review/hotspot aggregation still process their input scopes.
5. **History/fork compliance is outstanding.** Resolving it needs a deliberate repository decision that preserves the team's contributions. Updating a document cannot supply missing Git ancestry.
6. **Submission details remain team-owned.** Confirm names/roll numbers, contribution attribution, published final commit, demo link and required archive name. Deleted report/packaging helpers are not promised as available commands.
